# Security review 2: pairing, call control, phone data, diagnostics, IPC, payload

Second independent review of everything added after [security-review.md](security-review.md) (not repeated here): QR/token
pairing and discovery, call control, the contacts/calendar/SMS link, Copy report, unpair, the desktop clipboard
hotkey and local IPC, and the payload dial/listener changes of E2E-14. Read the code in `crates/bridge-kde`,
`bridge-service`, `bridge-android`, `bridge-core` and `android/app`. Nothing was committed.

Severity: High = remote or unauthenticated compromise of data or control; Medium = security-relevant weakness reachable by
a LAN stranger or another app; Low = needs an already-privileged position or only affects display.

## Checked and sound (no finding)

* **Token strength.** `TokenBook::issue` uses 16 random bytes (128 bit) from the system RNG; only SHA-256 digests are kept; comparison is constant-time over all live entries; single use; 120 s TTL; at most 4 outstanding; used tokens remembered (16) so reuse is reported as reuse.
* **Binding to the certificate.** The core compares the SHA-256 of the certificate on the live connection with `fp` before the token is sent (`transport_pair_request`, `qr_cert_sha256`), so a man in the middle never sees the token. The Android approver ignores a token presented by the computer; a computer-side token is only redeemed for incoming requests.
* **Skipping the scan.** Without a token the normal code comparison and explicit approval still apply (`a_request_without_a_token_still_waits_for_an_explicit_approval`). `qr_pinned` is set only when this side sent a token.
* **Payload dial/listener (E2E-14).** Both directions use the pinned-certificate verifier for the paired device (no inspect path); the sender drops connections whose source IP is not the paired peer before spending a handshake slot (8 at most, 4 s each) and keeps waiting after a failed handshake; the receiver only dials ports 1739-1764 on the peer IP of the control link (any port only with the dev switch `any_port`, set from `--dev-loopback` / the Android loopback policy only); the listener is consumed by `send`, so it closes with the transfer, on cancel and on timeout. The fallback source-address bind does not change what is trusted. Sizes and idle time are bounded.
* **Call control.** Gates are the desktop `Telephony` consent, the phone opt-in, `ANSWER_PHONE_CALLS`, and a check of the current call state on the phone (`CallRules.handle`); request ids are validated; only `acceptRingingCall` and `endCall` are used, no dialling. A paired computer that already has the consent can answer/decline; replay is limited to what the current state allows.
* **Phone data gate.** `gate::classify_incoming` routes only negotiated kinds; `phone_data` drops every packet when the per-device consent is off or nothing was requested, caps sizes, and erases on consent-off and unpair. Calendar writes need desktop consent, phone switch, `WRITE_CALENDAR`, a shared and writable calendar, refuse recurring events, take numeric ids only and are applied once per `opId` with a restart-safe ledger. Content URIs are built by the app from fixed authorities with `Uri.encode`d lookup keys; no URI comes from the peer. Nothing logs message, event or contact content (no `Log.*` in the app; no `tracing` in the data paths).
* **Copy report.** Versions, permission states and counts only, plus a scrubbed core-state line and the connection summary (counts); no names, numbers, addresses or fingerprints.
* **Unpair.** Local and peer-initiated unpair delete trust, consents, phone data, share and clipboard state (`forget_consent`) before any re-pair can inherit them.
* **Local IPC.** The control API is a loopback TCP port; every request carries an HMAC-SHA256 of the request under a 256-bit token kept in the 0700 state directory (file opened through `fsutil`, which refuses loose permissions and symlinks), with a per-connection nonce, constant-time check before parsing, a 3 s deadline and 8 concurrent exchanges. The token never crosses the socket. There is no peer-credential check (loopback TCP has none), so any process of the same user holding the token file can drive the service; another user cannot. The `paste-from-phone` hotkey binds only a validated `Mods+key` and a fixed command (`geekbridge-ctl clipboard paste-from-phone`).

## Changes made

* `bridge-service/src/daemon.rs`: `MAX_UNPAIRED_PER_IP = 3`; `install_ready` refuses a fourth unpaired link from one address and lets a paired phone displace the oldest unpaired link when the table is full (helpers `unpaired_from`, `oldest_unpaired`).
* `bridge-kde/src/qrpair.rs`: `TokenBook::redeem_from(token, now, source)`; wrong tokens counted per source (32 sources remembered); the lock-out no longer clears the live tokens; `redeem` keeps its old signature (source unknown = one bucket). `pairing_flow.rs` passes the link's peer IP.
* `bridge-service/src/notify_text.rs` (new) and its use in `call_control.rs`, `share.rs`, `phone_data.rs`; `--` before positional arguments.
* `docs/pairing.md` describes the new lock-out and link limits.
* New tests: `crates/bridge-service/tests/inbound_starvation.rs`, plus unit tests named in the table.

## Changes made for S2-4 to S2-10

* Android: `SendToComputerActivity` (confirm dialog, translucent theme), `ComputerGrants.kt` (grants, migration, runtime), `PhoneDataUi.kt` (`GrantsUi`), `SetupActivity.kt`, `AppState.kt` (paired ids), `Transport.kt` (`permits` always in the start request), `PhoneDataEngine.kt` / `PhoneDataProtocol.kt` (`RequestLedger`, `SmsDestination`), `CallControl*.kt`, `QrPairActivity.kt` / `QrPairing.kt`.

### Design calls left open

* Separate consent for reading versus sending SMS (S2-7): a UI/product decision; the destination check, the request-id ledger and the hourly cap now limit the cost of the shared consent.
* Per-computer rights are enforced for call control, contacts, calendar read/edit and SMS. Clipboard, file transfer and the other consents were not in S2-5 and stay as they were.
* The migration grants the old global switches to every computer paired at the first readable status after the update (the phone cannot tell which one the user meant); review them under "Allowed computers…".
