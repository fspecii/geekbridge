# Windows and macOS clipboard: secrets, change detection, encoding, Windows ARM64 updates

Closes four items of the "not fixed" list in [windows-macos-review.md](windows-macos-review.md).

## What changed

1. **Password-manager copies are no longer synced automatically on Windows and macOS.** The marker logic is pure code in
   `crates/bridge-service/src/clipboard_marks.rs` (tested on Linux with fixtures); the OS calls only collect the facts.
   * Windows: sensitive when the clipboard carries `ExcludeClipboardContentFromMonitorProcessing` or
     `Clipboard Viewer Ignore` (presence is enough), or `CanIncludeInClipboardHistory` / `CanUploadToCloudClipboard`
     with a DWORD of 0 (a value of 1, or an unreadable one, is not a mark). Names compare case-insensitively.
   * macOS: sensitive when the pasteboard lists `org.nspasteboard.ConcealedType`, `TransientType`,
     `AutoGeneratedType` or `com.agilebits.onepassword` (exact match).
   * Marked content is `Sensitivity::Sensitive`, so it takes the existing path in `bridge-core` (not sent on automatic
     sync, counted as skipped), the same as `x-kde-passwordManagerHint` on Linux. Both backends now report
     `reports_sensitivity`.
2. **No process per poll.**
   * Windows: `clipboard_win.rs` uses the Win32 API directly (the `windows` crate was already a dependency; features
     `Win32_System_DataExchange` and `Win32_System_Memory` added, no new crates). A thread reads
     `GetClipboardSequenceNumber()` every 250 ms and the service reads the text only when it moved; the 30 s safety
     poll of event sources stays. PowerShell is no longer started for reads or writes.
   * macOS: `NSPasteboard.changeCount` is read every 250 ms in the same way (`objc2-app-kit` feature `NSPasteboard`,
     already a dependency). `pbpaste` runs only after a change. The type list for sensitivity also comes from
     `NSPasteboard`, not from a process.
   * `ChangeStream` now has a counter source next to the process source (`wl-paste --watch`); its behaviour (one event
     per change, none for an unchanged counter) has a unit test.
3. **Windows encoding.** Clipboard text is `CF_UNICODETEXT` in both directions via `utf16_for_clipboard` /
   `utf16_from_clipboard` (NUL-terminated, interior NULs dropped, unpaired surrogate refused); round trips for
   accents, CJK, emoji and CRLF and exact code units are tested. `report::copy_to_clipboard` no longer pipes UTF-8 to
   `clip.exe`: on Windows it starts PowerShell once and passes the text as base64 on stdin (ASCII, so no code page
   can alter it); `clip` remains only as a last resort if PowerShell is missing. The base64 function is tested with
   the RFC 4648 vectors and a non-ASCII round trip.
4. **Windows ARM64 updates.** `bridge-update::select_asset` keeps picking `geekbridge-windows-aarch64.<ext>` (or
   `arm64`) for an ARM64 Windows machine; if a release has none it falls back to the x86_64 Windows archive (Windows 11
   on ARM runs x64 programs under emulation). An x86_64 machine never takes an ARM archive and the fallback never
   crosses operating systems. Tests cover native preference, no cross-arch pick, and no fallback to other OSes.
   `build-binaries.yml` has a `windows-aarch64` entry (target `aarch64-pc-windows-msvc`, cross-compiled on
   `windows-latest`; the smoke test is skipped because the x64 runner cannot run ARM64 binaries).

## Verified here

* `cargo fmt --check`, `cargo clippy --workspace --all-targets --locked -D warnings`, `cargo test --workspace --locked`
  on Linux (1844 tests passing).
* The type-check job (`scripts/xcheck.sh`, Windows x64, macOS arm64 and x86_64) and the Windows and macOS jobs of
  `check.yml` compile and lint the OS-specific files. No Windows or macOS Rust target is installed on the dev machine,
  so these were checked only by CI (the first pushes failed there on a wrong `GlobalFree` import and a clippy lint, fixed).
* `build-binaries.yml` run on `main`: windows-x86_64, windows-aarch64, macos-aarch64, macos-x86_64 and SHA256SUMS green
  (run 41662753593).

## Only a real machine can verify

Windows (x64 and ARM64):

* `OpenClipboard(GetDesktopWindow())` followed by `EmptyClipboard` and `SetClipboardData` actually replaces the
  clipboard (the desktop window is used as owner because a NULL owner can make `SetClipboardData` fail).
* A real KeePassXC, Bitwarden, 1Password or Windows' own "copy password" produces one of the marker formats and the
  copy is then not sent; that `CanIncludeInClipboardHistory` really arrives as a 4-byte DWORD through `GetClipboardData`.
* Emoji, accents and CJK copied on the PC reach the phone and back unchanged; CRLF handling for multi-line text.
* The 250 ms sequence-number check costs nothing measurable (idle CPU), and own writes do not loop (the existing echo
  suppression is relied on, as for polling before).
* Contention: another app holding the clipboard (6 attempts, 15 ms apart) does not drop a copy.
* The `report::copy_to_clipboard` PowerShell path with a non-ASCII diagnostics report, including under a hidden console.
* Windows ARM64: the `windows-aarch64` binaries start and run at all (they were only cross-compiled), and the updater on
  that machine picks the right archive from a real release.

macOS:

* `NSPasteboard` can be read from a background thread of the LaunchAgent service (changeCount and types) and Apple's
  pasteboard privacy prompt (macOS 15.4+ "paste from other apps" alert) does not appear for changeCount/types reads.
* Real 1Password, Bitwarden, KeePassXC and Keychain copies carry one of the four types.
* `pbpaste` is started only after a copy, not periodically (check with `sudo fs_usage` or Activity Monitor).
