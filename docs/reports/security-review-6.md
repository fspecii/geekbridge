# Security review 6: recent phone photos

Scope: `docs/design/recent-photos.md`, `docs/reports/recent-photos.md`, the packets `geekbridge.photos.request` / `.list` /
`.thumb`, the Android reader (`RecentPhotos.kt`, `RecentPhotosAndroid.kt`, MediaStore, `READ_MEDIA_IMAGES`, Android 14
partial access), the desktop store (`photos.rs`), the Share window tab (`photos_pane.rs`), `geekbridge-ctl photos`, the
expected-file exception in `share.rs`, and the scratch folder for clipboard copies. Viewpoints: a malicious paired
computer, a malicious paired phone, and a local observer (logs, terminal, UI).

## Fixed (with tests)

| id | viewpoint | finding | fix | test |
| --- | --- | --- | --- | --- |
| S6-1 | phone | The expected-file exception accepted the offer without looking at its size, so a phone could answer one Save click with a file of up to the 8 GiB transfer limit (or an unknown size) and fill the disk, with no prompt and no receive permission. | The offer must declare a size of at most 512 MiB (`MAX_PHOTO_BYTES`, the most a list may claim); otherwise the request fails with `too_large` and no transfer starts. The receive itself is capped at the same figure. | `an_offer_bigger_than_any_photo_fails_the_request_instead_of_filling_the_disk`, `an_expected_offer_is_claimed_once_and_only_when_it_is_the_size_of_a_photo` |
| S6-2 | phone | Finding the waiting request and marking it used were two separate lock holds, so two offers of the same name arriving together (two connections of one phone) could both be taken without the receive permission, "once" not being once. | The claim is made under the lock that finds it (`claim_expected` sets `Receiving`); a claimed request whose transfer cannot be created fails as `busy`. | same unit test (second claim is `None`) |
| S6-3 | computer revoking | Withdrawing the photos consent (or losing the link) forgot requests that were only waiting; a picture already arriving "was left to finish" and kept writing into the save folder or scratch folder, and a finished clipboard copy stayed on disk for ten more minutes. | `drop_expectations` now cancels a download in progress (partial file removed), forgets the request, and erases a finished clipboard copy of that phone. Saved photos stay (the user asked for them). | `withdrawing_photos_cancels_a_picture_that_is_still_arriving` |
| S6-4 | local / phone | The scratch folder was created with `create_dir_all(0700)` only when missing. A pre-existing folder with loose permissions stayed loose, and a symlink at `.geekbridge-photo-copy` (planted, or left behind) was followed: clipboard copies would be written wherever it pointed. | `make_private_dir` refuses a non-directory, replaces a symlink by a real directory (never touching the target), and tightens permissions to 0700; if that fails the transfer fails (`scratch_unsafe`) and nothing is written. | `a_planted_link_in_place_of_the_scratch_folder_is_not_followed`, `the_scratch_folder_is_a_private_real_folder_never_a_planted_link` |
| S6-5 | crash | "Emptied at start" was not true: the start sweep only removed files older than ten minutes, so a copy from a run that crashed a minute ago stayed. Links were also never swept. | At start everything in the scratch folder goes (regular files and links, as links; no recursion, nothing outside is touched). The ten-minute rule remains for a running service. | `a_new_manager_empties_what_a_crashed_run_left_in_the_scratch_folder` |
| S6-6 | phone | A phone could list a "photo" named `run.sh`, `x.lnk` or `a.desktop` with a fine-looking thumbnail; one Save click then dropped that file, named as the phone chose, in the save folder with no receive prompt. | Only names with a picture extension (jpg, jpeg, png, gif, webp, heic, heif, avif, bmp, dng, tif, tiff, jxl) are kept from a list; others are never shown or fetchable. | `a_listed_name_that_is_not_a_picture_is_never_kept`, `only_picture_names_pass_the_image_name_check` |
| S6-7 | phone / UI | The clipboard path handed whatever arrived (any bytes, up to the cap above) to `wl-copy`/`xclip` labelled `image/jpeg`, and to PowerShell `Image.FromFile` on Windows, with no check of type or size: a mislabelled file on the clipboard, and a decompression bomb for the system decoder. The preview decoder was already safe (header checked, 256 px). | `check_picture` runs before any tool: regular file (not a link), at most 128 MiB, starts like its type (JPEG, PNG, GIF, WebP), and the header (parsed, not decoded) may claim at most 100,000 px a side and 250 megapixels. Otherwise a new line explains and Save still works. | `a_received_file_is_checked_before_a_clipboard_tool_or_image_decoder_sees_it` |
| S6-8 | phone / UI | File names kept U+061C (Arabic letter mark) and U+2028/2029; `sanitize_filename` (every received file, photos included) kept all bidirectional controls, so `photo<RLO>gpj.exe` saved and displayed as `photoexe.jpg`. | `clean_text` also drops U+061C and turns U+2028/2029 into spaces; `sanitize_filename` maps every bidirectional control and the line separators to `_`; the Android lister refuses the same characters so both sides agree on the name. | `names_lose_every_text_reordering_or_line_breaking_character`, `sanitises_names` (two new rows), `namesWithAnArabicLetterMarkOrLineSeparatorAreNotListed` |
| S6-9 | computer asking | The phone answered every `thumb`, `list` and `get` it received from an allowed computer, with no pace: a hostile (or buggy) computer could request thousands of thumbnails and make the phone decode media in a loop (CPU, battery, the engine lock). The phone's outgoing limit does not slow the reading. | Per-connection token buckets in `RecentPhotos`: thumbnails burst 60 then 8 a second (exactly the desktop's own pace), lists burst 4 then one per 2 s, full pictures burst 3 then one per 5 s; excess is ignored. | `aComputerThatAsksFasterThanAPersonCouldIsIgnored` |
| S6-10 | computer asking | Ids were one pool for all connections, so a second allowed computer could `get` or `thumb` an id that was handed to the first, without ever listing it. | Ids are bound to the connection they were given to. | `onlyListedIdsCanBeAskedForAndAFullPictureNeedsAGetOfAListedId` (updated) |

## Checked, no change needed

- **Enumeration beyond "recent N" / consent.** The list is `latest(limit*2)`, newest first, `limit` 1..24 from a strict parser; MediaStore returns only what Android lets this app see (Android 14 partial access narrows it to the picked photos, and `exists()` re-queries before a `get`). Ids are `p<counter>`, never media ids; a media id such as `2`, or `../x`, is refused by the id charset and by the lookup. Repeating `list` returns the same newest 24; there is no offset or cursor.
- **Path traversal / arbitrary read via the `get` id or name.** The id is `[A-Za-z0-9_-]{1,32}` on both ends and is only a key into the phone's own table; the computer's request carries no path. The name that decides where a file lands is `sanitize_filename` of the listed display name (last path component, control and Windows-reserved characters replaced, no leading dot, reserved device names prefixed, length cut), then `reserve_unique` (`create_new`, ` (1)` suffixes, rename of our own temp file). Test `saving_never_replaces_a_file_that_is_already_there` pins the no-overwrite rule on Save.
- **Reading photos with the switch off / grant revoked mid-session.** Phone: `enabled()` and `port.access()` are read on every request; the native core drops a request from a computer not on the per-feature list at arrival and refuses to send photo packets to one (`permitted_ctls`), so a reply to a revoked computer goes nowhere. Computer: `on_photos_packet`, `photo_thumb` and `photo_fetch` check the consent on every call; withdrawal erases the store. Residual: a `get` already queued in the engine when the grant is revoked can still start one file send (the file offer is then refused by the computer unless it is waiting for it); window is milliseconds.
- **Unsolicited list / thumb / file.** List only within 30 s of asking and once; thumbnail only for a pending id, once; payload-bearing photo packets are counted as rejected and the link is dropped after the usual limit; an unasked file offer is refused (`a_full_picture_is_taken_only_because_it_was_asked_for...`). Window of two minutes, per phone and per exact sanitised name; 4 waiting per phone, 8 in all.
- **Computer memory / CPU.** 24 entries, 8 phones, 2 MiB of thumbnails in all; the desktop asks for at most 24 thumbnails per list and 4 are fetched through the control API per window cycle; JPEG previews are decoded on the worker thread, header-checked to 256 px before decode, 24 KiB and base64 length checked before decode; `Unsupported` for CMYK. Textures are bounded to 24.
- **EXIF/GPS in thumbnails.** Thumbnails are produced by `loadThumbnail` / a sampled decode and re-encoded with `Bitmap.compress`, which writes no EXIF. **Full pictures:** `ACCESS_MEDIA_LOCATION` is not requested, so on Android 10+ the media store redacts the GPS tags in the stream the app reads. On Android 8-9 (API 26-28) there is no redaction (see residual 1).
- **Malformed image crashing the GUI.** `jpeg-decoder` is pure Rust and returns errors; the pane never decodes full pictures; decode failures leave the cell without a preview. The deterministic fuzz run of `photos_wire` passes.
- **Logs.** No logging in `photos.rs`, `photos_pane.rs`, the photo code in `share.rs`, or the Kotlin photo files; no event carries a name; `geekbridge-ctl photos` prints names on purpose (like `notifications`), after control characters are replaced by spaces.
- **Permissions.** Manifest has `READ_MEDIA_IMAGES`, `READ_MEDIA_VISUAL_USER_SELECTED`, `READ_EXTERNAL_STORAGE` (max SDK 32) and nothing for video, audio, location or all-files access.
- **i18n / bidi in UI.** Names from the phone are cut to 100 characters and stripped of bidirectional controls before they reach any label, the CLI or the AccessKit tree.

## Residual risk / recommendations (not changed)

1. Android 8-9: a full picture sent by Save/Copy carries its original EXIF including GPS. Stripping needs a re-encode or an EXIF writer on the phone; documented in the design note instead.
2. Android: the id table is cleared on link loss and feature change, not on a per-computer grant revocation; ids of a revoked computer stay valid for that connection id only, and the native core drops its requests anyway.
3. A malicious phone can still send arbitrary bytes under a picture name (at most 512 MiB, once per click, into the save folder with a unique name). Saving does not verify content; only Copy does (S6-7).
4. Copy leaves the scratch file until the ten-minute sweep; deleting it right after the clipboard tool exits would shorten that.
5. Windows and macOS clipboard paths are still not exercised; the new header check protects them, but real runs are needed.
6. Not run on a real phone (as in `recent-photos.md`): MediaStore redaction on Android 10+ is documented platform behaviour, not observed here.
