# Security review 7: QR pairing, dev update channel, call card, Bluetooth call setup, call-audio experiment

Scope: everything new since `security-review-6.md` in six areas. (1) QR pairing: `pairing_decode_qr` and the `rqrr`
decoder, the in-app scanner, the `geekbridge://pair` link, the desktop code and its renewal. (2) The dev update channel:
manifest and asset trust, signer handling, `scripts/release-dev.sh`, `.github/workflows/dev-release.yml`. (3) The
incoming-call card spawned by the service. (4) Bluetooth call setup: the BlueZ agent, `call setup --fix-config`, the
state files. (5) The notification, share and photos result packets. (6) The experimental Wi-Fi call audio.
Viewpoints: another app on the phone, a stranger in Bluetooth or camera range, a party that can edit the GitHub release,
a local process of the same user.

## What was checked and needs no change

**QR pairing**
- Token: 128 random bits (`random_bytes`), only the SHA-256 is kept, compared without early exit, single use (used list), 120 s life, per-source lock-out after five wrong tokens that does not revoke the owner's code. The phone checks the certificate on the live connection against the pinned fingerprint before it sends the token (`engine.rs` `pair_request`, `qr_certificate_mismatch` closes the connection), so the token never goes to a man in the middle. Replay of a used or expired code: `AlreadyUsed` / `Expired`. Racing the expiry: `redeem_from` checks `expires_ms <= now` under the book's lock.
- The phone cannot be made to show a different computer than the one it dials: name, address and fingerprint on the confirm page come from the same parsed link, marked "not verified", with the name cleaned, bounded to 40 characters and wrapped in bidi isolation. Any app (or a web page) can open `geekbridge://pair` but that only reaches the confirm page; the deep link is the only exported component of the pairing flow (`QrScanActivity` is not exported, its result goes to the calling activity).
- Camera frames: grey bytes are base64'd into one request, decoded in memory by the core and dropped; no file, no log line, no `Log.*` of requests, the link text is never logged. The camera is held only while the scan screen is open.
- The invite text is a public URL (`ComputerInvite.body`), no token, no address.
- Unlink flows: `Forget` before re-pair is bounded by 5 s (`FORGET_WAIT_MS`); the desktop closing the dialog or leaving the page sends `PairQrCancel`.

**Dev channel**
- Manifest: `commit` hex 7..40, `versionCode` in 20001..2e9, size 16 KiB, notes capped; assets must come from the fixed GitHub hosts over https (`urlAllowed`, `url_allowed`), redirects re-checked per hop, no credentials ever sent from the phone; asset names pass `safe_file_name` (no separators, no leading dot, no `..`) and the file is stored under a fixed name on the phone and in a fresh private directory on the desktop; sizes are capped (200 MiB APK, `MAX_ASSET_BYTES`) and enforced while streaming and again by byte count; the SHA-256 is computed while writing and compared with the listing, and again right before the hand-off.
- Downgrade and replay: the manifest only decides "newer?"; the phone refuses a file that is not newer and Android refuses a downgrade. Only `geekbridge-debug.apk` is ever offered on the dev channel. Channel switching: separate ETag caches; a release build asks for confirmation before it follows dev and warns that Android will refuse the dev signature.
- The signer pin: `GB_DEV_SIGNER_SHA256` is enforced where the APK is built and published (`release-dev.sh`, the signing step of `dev-release.yml`), and the app enforces the stronger rule, the key of the build that is already installed (`SignerCheck`: mismatch is a stop, with the fingerprints shown, and the file is deleted). A compromised release cannot put its own key on a phone that has the owner's key.
- `release-dev.sh`: typed `publish dev` confirmation unless `--yes`; dirty tree, non-main branch and "origin/main ahead" are refused; the manifest is uploaded last; the tag moves with the API; "latest" is verified not to be `dev`; the keystore is never copied, passwords are not on its command line or in its output; every `gh` argument is a separate word (no `eval`, no shell string), `--repo` is passed as one argument. Python gets arguments with `-I`.
- `dev-release.yml`: triggers are `push` to main and `workflow_dispatch`; no `pull_request` or `pull_request_target`; permissions `contents: read`, with `contents: write` only on the publish job; all actions pinned by commit; no expression from event data is expanded in a `run:` block (matrix values and booleans only); the publish job takes artifacts of its own run and `release-dev.sh` accepts only fixed file-name patterns from them.

**Call card**
- The service starts `geekbridge-calls --overlay --api-port N [--name-only]` with the fixed program name and two environment variables (state folder, control port) plus display variables. No caller name, number or any phone data goes into the arguments or the environment, so there is nothing to inject into; the card reads the call from the service API like the Calls window and answers through the same call-action path (`request_for`), under the same local control token. The privacy mode is read from `GEEKBRIDGE_CALL_OVERLAY` or the `call-overlay` file by the service and passed as `--name-only`; the card never draws the number in that mode (`caller_lines`). Text is truncated in the card and egui does not reorder bidirectional text.

**Result packets and fuzzing**
- `geekbridge.share.result` goes from computer to phone only, is accepted only for a share this phone made on that same connection id (`incoming_share_result` checks connection, direction and kind; text ids are checked against `texts_sent`), and the first answer stands. A second phone cannot answer for the first. Parsers for share, share result, notification, photos, calls, clipboard, vcard, agenda and the Android dispatcher have fuzz targets and regression tests in `bridge-fuzz` (this review adds the `pairing_decode_qr` seed).

**Experimental Wi-Fi call audio**
- It lives in `experiments/callaudio-wifi` (not a workspace member, no product crate depends on it) and, on the phone, in `android/app/src/debug/.../callaudio/` (debug source set only). `scripts/check-release-isolation.sh` fails a release dex that contains `CallAudioHelper`, `HelperSession` or the package. The gate (`gate.rs`) takes the two consent flags and the call state only from local setters (`set_consent`, `set_call_active`), never from a packet; a remote `Request` still needs the phone switch and a live call, an `Offer` needs the computer's consent, frames outside a live session, in the wrong direction or over 75 a second are dropped and counted, and a session ends after 5 s of silence. The shell helper listens on an abstract socket whose name is random, accepts only uid 0, 2000 or the given app uid (`peerCredentials`; an unreadable credential is refused), requires a random token before any command or injected audio (`MessageDigest.isEqual`), and serves one client at a time. Nothing is built into release artifacts.

**Bluetooth setup**
- The agent is registered only for the duration of `run`, with capability `DisplayYesNo`; `RequestConfirmation` and `RequestAuthorization` always go to the user and time out below BlueZ's 60 s; PIN and passkey entry are refused; nothing is auto-accepted. Discoverable and pairable last `discoverable_for` (120 s) and are put back to the values found at the start on every exit path (`restore`). Trust is set on the one device the setup returns, before the agent is dropped. `--fix-config` writes only `zz-geekbridge-call-audio.conf` beside the user's files, validates it with its own SPA-JSON checker and `spa-json-dump` before it is put in place, restarts WirePlumber and rolls back if it does not stay up.

## Residual risk and recommendations (not changed)

1. A person within Bluetooth range who starts a pairing during the 120 s window still produces a code prompt; the user must compare the code with a phone they hold, and now sees the device address. The setup adopts the device whose code the user confirmed, by design (phones show a model name, not the GeekBridge name).
2. S7-14: when a link claims the id of a computer the phone already trusts, the confirm page does not say so. A short "this replaces your link with X" line would make the consequence visible.
3. `release.yml` and the dev signing job can be dispatched from any branch; only a GitHub environment restricted to `main` protects the keystores. Please create the environments and move the secrets (see `docs/updates.md`).
4. If setup is killed with SIGKILL the adapter keeps `Pairable` until BlueZ is told otherwise (discoverability ends by itself through `DiscoverableTimeout`).
5. The call card answers on Enter when it has keyboard focus; the Windows style never activates the window, but a Wayland compositor that focuses new windows could route a keystroke to it. Consider answering only by click.
6. The overlay's fallback display discovery (`/tmp/.X11-unix`) takes the first X socket without checking its owner; X authority still protects it.
7. Desktop dev and stable installers are verified by SHA-256 only (S7-13); signing them is a release-process decision.
