# Android real-device risks

> Status: snapshot from 2026-11-02, see git history for later changes. Numbers and findings below describe that point in time, not necessarily the current tree.

Review of `android/app/src/main` for behaviour an emulator hides (targetSdk 36, tested reasoning for Android 14–16,
OEM skins). Evidence is `file:line` in `android/app/src/main/` unless noted. Status: **OK** (verified by reading),
**FIXED** (changed in this review, with a unit test), **OPEN** (known, not changed), **DEVICE** (only a phone can confirm; see
`docs/real-device-test-plan.md`).

## 2. Doze and network behaviour

| Risk | Evidence | Status |
|---|---|---|
| Network change: `registerDefaultNetworkCallback` with main-handler, unregistered in `onDestroy`; a new default `Network` restarts the link once, debounced 3 s, first callback ignored; restart retries are bounded (6 × 500 ms) and respect `needsLink()` so a running transfer is not cut. | LinkService.kt:80-127, 63-69 | OK |
| **IP change on the same `Network`** (DHCP renewal, roam to an AP on another subnet, VPN toggle) produced no callback the service used, so the phone kept announcing its old address until the next network switch. `onLinkPropertiesChanged` now compares the IPv4 set (IPv6 privacy rotation ignored) and schedules the same debounced restart. | LinkService.kt:94-101; ServicePolicy.kt:14-17 | **FIXED** (`DeviceRisksTest.ipv4Change…`) |
| Multicast lock only while discovery listening is on: Share (`geekbridge-share`, released in `onStop`), PairPanel and LinkSection (`geekbridge-discovery`, released when listening ends or the screen leaves the foreground). `LinkService` never listens, so it never holds one. Non-reference-counted, so a double acquire cannot leak. | ShareActivity.kt:260-275, 74; PairPanel.kt:197-210; LinkSection.kt:436-459; LinkService.kt:80 | OK |
| No wake locks anywhere in the app (grep `WakeLock`: none). Screen off / Doze: sockets sleep, the Rust transport relies on kernel TCP keepalive and a UDP announce; the app has no timers or polling in the service. Android 12+ Doze delays inbound data until a maintenance window unless the battery exemption is granted, hence the setup step and the "battery optimisation is on" notification text. | LinkService.kt:20-26; Power.kt | OK / DEVICE |
| Reconnect backoff lives in the Rust transport (`crates/`), not Kotlin; the Kotlin side only restarts after a network change (debounced). Not reviewed here. | LinkService.kt:106-127 | DEVICE |
| `lastNetwork` is not cleared on `onLost`; a lost-then-same-`Network` return is not a case Android produces (a new `Network` object is created). | LinkService.kt:84-92 | OK |

## 3. Clipboard, tile, PROCESS_TEXT, share, edge-to-edge

| Risk | Evidence | Status |
|---|---|---|
| Android 10+/13+ clipboard: reads happen only in `ClipboardFloatingActivity.onWindowFocusChanged(true)` (tile, notification tap, Home button); writes (`setPrimaryClip`) are allowed in background. `IS_SENSITIVE` extra honoured; `SecurityException` caught. Android 13's "pasted from" confirmation and 12's read toast are system UI and unavoidable. | ClipboardFloatingActivity.kt:25-41; ClipboardAndroid.kt:30-45, 100-122 | OK |
| Tile: `startActivityAndCollapse(PendingIntent)` on API 34+ (the Intent overload throws), `unlockAndRun` when locked, `BIND_QUICK_SETTINGS_TILE` permission. | ClipboardTileService.kt:26-41 | OK |
| `PROCESS_TEXT` activity is exported (required) but shows the text and needs a tap before anything is sent; read-only. | SendToComputerActivity.kt:20-55 | OK |
| `ContentResolver.getType(uri)` used to run on the main thread inside `onWindowFocusChanged` against a provider chosen by whoever put an image on the clipboard. Now focus only takes the `ClipData` reference (`AndroidClipboardHost.grab`); `snapshot` runs on the clipboard worker and `ClipReader` bounds the provider probe at 2 s (`BoundedCall`, falls back to the clip's declared type). `withImageFd` opens with `openFileDescriptor` + `CancellationSignal` (2 s) and bounds the copy (15 s, stream closed on timeout). | ClipboardAndroid.kt; ClipReader.kt; ClipboardFloatingActivity.kt; ClipboardRuntime.kt | **FIXED** (`ClipReaderTest`) |
| **Queued shared files opened after the Share screen was gone.** `ACTION_SEND` content-URI grants are tied to the receiving activity; the old code opened each file only when its turn came (one at a time, ≤50) so file 2…N failed with `SecurityException` ("Could not open this file") once the user pressed Hide or the activity finished, while the UI promised "keep going in the background". Now every file's name, size and read descriptor are opened by a prefetch thread as soon as the session starts and the descriptor is held until the core takes it (handed back on `busy`); revoked grants after that no longer matter. Covers Gallery/Google Photos/Chrome. `persistableUriPermission` is not offered for `ACTION_SEND`, and copy-on-start would double storage for large videos. | ShareCoordinator.kt:219-232, 283-330; EarlyOpen.kt | **FIXED** (`DeviceRisksTest.earlyOpen…`) |
| Share screen queried the provider's `DISPLAY_NAME` for up to 5 URIs on the main thread on every `render()` (every state change/poll). Photos/Drive providers can block for seconds → jank/ANR. Names are now resolved once on a background thread and cached. | ShareActivity.kt:107-140 | **FIXED** |
| Android 14 partial photo access: the share flow never needs `READ_MEDIA_*` (it reads the exact URIs the picker/Photos granted); received files go through `MediaStore.Downloads`, no storage permission. Large video from Photos: some providers return a pipe or no size; the app then reports "the app providing this file does not report its size" instead of hanging. A copy-to-cache fallback for size-less providers would make these work. | ShareCoordinator.kt:300-306; ReceivedFiles.kt | OK / OPEN (size-less providers) |
| Edge-to-edge (Android 15 enforced at targetSdk 35+): `SystemBars.setup` + `Screen` insets pad content and footer for status/nav bars and cutouts; `statusBarColor` is ignored on 15 and no opt-out flag is used. Dialog-themed `ShareActivity` is floating and exempt. | UiKit.kt:326-343, 358-390 | OK / DEVICE |
| Predictive back: `enableOnBackInvokedCallback="true"`; `SetupActivity` registers an `OnBackInvokedCallback` only while Back means "previous page" so the system back-to-home animation plays on page 0; other screens do not override `onBackPressed`. | AndroidManifest.xml:60; SetupActivity.kt:47-83 | OK |

SMS/WRITE_CALENDAR via `PhoneDataUi` (request on toggle, Grant button, app-settings button). | SetupModel.kt:6-18, 126-160; SetupActivity.kt:178-190; PhoneDataUi.kt:30-54 | OK |

## 5. Crash resilience, native library, ANR

| Risk | Evidence | Status |
|---|---|---|
| **No uncaught-exception handler and no `Application` class**: a crash left nothing for the Diagnostics report. Added `GeekBridgeApp` (declared in the manifest) installing `CrashNote`: writes a redacted note (exception class names, 8 frames, thread name, version; **never the message**) to `filesDir/last-crash.txt`, then chains to the previous handler. Diagnostics report prints it as `last crash:`. | GeekBridgeApp.kt; CrashNote.kt; DiagnosticsReport.kt; AndroidManifest.xml:53 | **FIXED** (`DeviceRisksTest.crashNote…`) |
| **No StrictMode in debug** — main-thread disk/network and leaked closables were invisible. `GeekBridgeApp` enables `detectAll()` thread and VM policies with `penaltyLog` only in debug builds. An emulator sweep (Home, Share text/file, Contacts, Calendar, Calls, Messages, Setup, Diagnostics) found only first-touch disk reads of `filesDir` and SharedPreferences on the main thread (HomeActivity/ShareActivity/ClipboardRuntime); `GeekBridgeApp` now warms them on a worker, and the re-run logged no violations. | GeekBridgeApp.kt | **FIXED** |
| Native library failure: `System.loadLibrary` failure is recorded (`UnsatisfiedLinkError`, `SecurityException`) and every `CoreClient.call` returns `Unavailable` (also on `LinkageError`/`RuntimeException` during the call); UI shows "native core unavailable". | NativeBridge.kt:16-25; CoreProtocol.kt:132-146 | OK |
| ABIs: APK ships `arm64-v8a` and `x86_64` only (`abiFilters`), verified at packaging. A 32-bit-only device (some low-end phones run a 32-bit userland on 64-bit CPUs) refuses the install (`INSTALL_FAILED_NO_MATCHING_ABIS`) rather than crashing at start. x86 (32-bit emulators) is the same. Documented contract: "phone and emulator only". | app/build.gradle.kts (`packagedAbis`, `verifyNativeLibs`) | OK (by design) |
| JNI/IO on the main thread: `TransportController` runs every native call on `geekbridge-transport`; other runtimes use their own named worker threads (`clip-send`, `calls-send`, `data-send`, `grants`, `update`, `share`); the long `wait` calls run on dedicated daemon threads; `MainActivity` documents "first touched on the worker thread". Remaining main-thread provider calls: clipboard `getType` (OPEN above). Share `displayName` (FIXED above). | TransportController.kt:68-75; LinkRuntime.kt:36-55; grep `Thread(` | OK except as listed |
| `LinkService.onStartCommand`/`onCreate` only touch `SharedPreferences` (`AppState.init`) and post to the worker; first `SharedPreferences` read may touch disk once on the main thread. | LinkService.kt:38-47 | OK (StrictMode will log it) |
